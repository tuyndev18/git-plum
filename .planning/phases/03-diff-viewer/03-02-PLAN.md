<!-- Chạy git thật trên máy này (git 2.54.0.windows.1), 2026-09-21. Không đọc lại tài liệu. -->

**1. `git cat-file --batch-check` cho kích thước blob chính xác mà KHÔNG đọc nội dung:**

```
$ git rev-parse HEAD:.planning/STATE.md | git cat-file --batch-check
206878cc12b0a23ba14b9b25bdabde2c0618552e blob 49648
```

Đây là cách đúng để làm cổng ngưỡng kích thước: biết kích thước **trước** khi đọc byte
nào. Đọc blob rồi đo `len()` thì đã nạp 200 MB vào RAM, tức đã thua trước khi kiểm.

Dạng dòng: `<oid> SP <type> SP <size> LF`. Blob không tồn tại cho
`<oid> SP missing LF` — phải xử lý, không `unwrap`.

**2. `git diff --numstat -z` báo `-\t-\t` cho tệp nhị phân:**

```
$ git diff --cached --numstat -z -- c.bin | od -c
0000000   -  \t   -  \t   c   .   b   i   n  \0
```

Hai dấu gạch ngang thay cho số dòng thêm/xoá. Đây là cổng nhận biết nhị phân **rẻ nhất**
và dùng chính phán quyết của git, không phải phép đoán "có byte 0 trong 8000 byte đầu"
tự viết.

**3. `git check-attr` KHÔNG nhận ra con trỏ LFS nếu repo không có `.gitattributes`:**

```
$ git check-attr -z filter -- d.lfs | od -c
0000000   d   .   l   f   s  \0   f   i   l   t   e   r  \0   u   n   s
0000020   p   e   c   i   f   i   e   d  \0
```

Trả `unspecified` cho đúng một tệp **là** con trỏ LFS. Đây là câu trả lời cho câu hỏi 3
của CONTEXT.md, và nó ngược với phỏng đoán trong câu hỏi ("`check-attr` đúng hơn"):
`check-attr` trả lời câu "repo này có **cấu hình** LFS cho path này không", không trả lời
câu "blob này **có phải** con trỏ LFS không". Một repo clone về mà chưa cài `git-lfs`, hay
một tệp con trỏ còn sót sau khi `.gitattributes` bị xoá, đều cho `unspecified`. Dạng `-z`:
`<path>\0<attr>\0<value>\0`.

**4. Dạng con trỏ LFS** (spec v1, ba dòng đầu, luôn ASCII):

```
version https://git-lfs.github.com/spec/v1
oid sha256:<64 hex>
size <số thập phân>
```

Con trỏ LFS **luôn nhỏ** (~130 byte) và **luôn ASCII** — nên nhận biết bằng nội dung là
việc rẻ: chỉ cần đọc blob khi `size < 1024`.

**5. Tiền tố `a/` `b/` được bảo đảm** vì `diff.noprefix=false` đã ghim trong
`PINNED_GIT_CONFIG` của `exec.rs`. Bộ phân tích dựa được vào điều này, và `exec.rs` có
test đọc ngược giá trị đó từ tiến trình con.

`src-tauri/src/domain/diff.rs` — hợp đồng dữ liệu, `#[serde(rename_all = "camelCase")]`
trên mọi struct/enum:

- `enum LineKind { Context, Added, Removed }` — serialize thành `"context"` / `"added"` /
  `"removed"`.
- `struct DiffLine { kind: LineKind, content: String, old_line: Option<u32>,
  new_line: Option<u32>, no_newline_at_eof: bool }`
- `struct Hunk { old_start: u32, old_count: u32, new_start: u32, new_count: u32,
  heading: String, lines: Vec<DiffLine> }` — `heading` là phần sau `@@` thứ hai (git đặt
  tên hàm chứa hunk vào đó; hữu ích cho DIFF-03 khi nhảy giữa các hunk).
- `enum DiffKind` — **enum có dữ liệu**, serialize dạng
  `#[serde(tag = "kind", rename_all = "camelCase")]` để phía TS phân biệt được bằng
  `discriminated union`:
  - `Text { hunks: Vec<Hunk>, truncated: bool }`
  - `Binary { old_size: u64, new_size: u64 }` — **không** trường nội dung nào
  - `TooLarge { size: u64, limit: u64 }`
  - `LfsPointer { oid: String, size: u64 }`
  - `Unchanged` — hai phía giống nhau (xảy ra với commit chỉ đổi mode tệp)
- `struct FileDiff { path: String, old_path: Option<String>, status: String,
  kind: DiffKind }`

`src-tauri/src/git/parsers/patch.rs` — `parse_patch(stdout: &[u8]) -> PatchParse` với
`PatchParse { hunks: Vec<Hunk>, truncated: bool, skipped_lines: usize }`.

Cách viết, và vì sao:
- Tách dòng theo `\n` bằng `memchr` (đã có trong `Cargo.toml`), rồi **cắt `\r` cuối mỗi
  dòng**. Làm việc trên `&[u8]`, không trên `String` — đầu ra git là byte.
- Bỏ qua mọi dòng trước `@@` đầu tiên (`diff --git`, `index`, `---`, `+++`). Không phân
  tích đường dẫn từ header: `get_file_diff` **đã biết** path (nó truyền vào), nên đọc lại
